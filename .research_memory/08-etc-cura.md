# ETC 基线审计与 CURA 主线记忆

> 最近更新：2026-07-17。本文是当前研究主线的稳定入口；如与旧的 ReasonRAG、LogicRAG、DocRE 记录冲突，以本文和最新决策日志为准。

## 1. 当前研究目标

- 底座：ETC，属于动态、及时检索 RAG。
- 保留的大方向：根据生成状态决定何时引入外部检索，并联合考虑查询内容。
- 不做：按数据集继续调 alpha、只换模型、只加参数、把若干技巧拼接、online RL。
- 工程原则：原 ETC 代码、配置和结果冻结；后续实现全部增量新增，通过配置切换。

## 2. ETC 已确认事实

- 论文原文和论文开源代码确实不同。
- 论文触发为平滑二阶熵差的绝对值超过数据集特定阈值；开源代码实际还引入注意力加权，默认主要检查正向值，且内部平滑变量也命名为 alpha，存在语义混淆。
- 查询沿用 DRAGIN/QFS 风格：根据注意力从问题和生成前缀中选择内容词，属于启发式查询。
- BM25 每次返回 top-3，文档无质量验证即进入后续生成；旧路径没有查询/文档去重、证据拒绝和明确预算控制。
- 用户将开源代码的低效离线检测改为在线执行，目标是保持算法效果等价并提高效率；该改动定位为工程优化，不作为论文贡献。正式报告仍应以固定样本的触发位置、查询、文档和答案轨迹验证等价性。

## 3. HotpotQA 复现与评测口径

- 运行：Llama3-8B、HotpotQA 1000 条、在线检测、threshold/alpha=1.0，后台双 GPU worker 并行；完整性检查通过。
- 服务器运行目录：`result/hotpotqa_online_alpha1_parallel`；控制日志：`controller_dual_gpu.log`。
- 原始仓库抽取：`EM=0.3050 / F1=0.4268`。
- 修正重复答案抽取：`EM=0.3740 / F1=0.4924`。当前实际代码模式名为 `first_answer_span`：从第一个 `the answer is` 后开始，在下一个重复答案标记或问题尾部前截断；它不是“取最后一个答案”。口头描述与实际代码存在差异，后续以版本化实现和单测为准。
- 论文报告：`EM=0.272 / F1=0.487`。修正版 F1 接近论文，但 EM 高 10.2 个百分点，不能宣称完全复现。
- 1000 条中 231 条答案变化，169 条至少重复两次答案模板；修正版保留原有 305 条 EM 并新增 69 条，无正确→错误。新增 EM 中 47 条、F1 提升中 99 条直接来自重复模板。
- 报告规则：复现表同时列原始与修正抽取；方法主表统一采用版本化修正抽取器，附录报告原始口径、重复答案率和逐样本变化。

## 4. 当前核心问题

用户否定把调用、延迟和上下文成本预设为主学术动机：本地 BM25/Elasticsearch 调用可能很便宜，上下文开销也必须实测。成本、延迟和 token 仅作为次要报告指标。

当前更可信的问题是：

1. 局部不确定性不等于外部证据会改善答案；模型可能自信地错，也可能只是语言层面不确定。
2. 外部证据是状态依赖的信息干预，可能产生正、零、负效应，包括无关、冲突、冗余、错误锚定和正确→错误污染。
3. 生成早期知识缺口可能尚未明确，查询含糊；合适阶段缺失实体/关系已经显现，查询最可检索；过晚又可能发生错误传播。因此存在“查询就绪窗口”。
4. 触发和查询不应是割裂管线：是否存在一个可靠的正收益查询，本身应决定是否检索。

## 5. CURA 修订版

暂定名称：CURA（Counterfactual Utility-calibrated Retrieval Action），中文建议写“校准的反事实检索收益动作选择”。utility 主要指答案效应，不再指成本加权净效用。

状态：

\[
s_t=(x,y_{<t},\phi_t,h_t),
\]

其中 `x` 是问题，`y_<t` 是前缀，`phi_t` 包含 ETC 趋势、margin、位置、命题/缺口表示，`h_t` 是检索历史。

动作：

\[
\mathcal A_t=\{skip,q^{QFS},q^{question},q^{gap},q^{entity}\}.
\]

同一状态下离线执行 skip 与查询分支，定义：

\[
B_t(q)=S(Y_t^q,y^*)-S(Y_t^{skip},y^*).
\]

- `B>0`：有益检索；`B=0`：无效/冗余；`B<0`：有害检索。
- 训练轻量预测器 `g_theta(s_t,q)` 预测查询收益；生成器和检索器冻结，不做 online RL。
- 独立校准集构造选择后的一侧下界：

\[
LCB_t(q)=g_\theta(s_t,q)-c_\delta.
\]

- 查询选择：`q*=argmax_q LCB_t(q)`。
- 检索时机：首次满足 `max_q LCB_t(q)>0` 的生成位置。
- 若所有查询下界不为正，则继续生成。

## 6. 新颖性边界

以下内容单独做都不够新：动态检索、knowledge boundary、知识缺口查询、噪声过滤、联合 when/what、证据效用、轻量分类器。

必须保留的组合差异：

1. 生成中间状态上的 `skip + 多查询` 同状态配对终局结果；
2. 查询特异收益，而不是状态级不确定性或单条轨迹奖励；
3. 在多个生成位置上学习收益曲线与最早正收益时刻；
4. 对候选最大值选择后的动作做一侧风险校准；
5. 跨数据集不调目标集阈值，重点报告负收益检索与正确→错误翻转。

最邻近工作：SKR、Self-RAG、CRAG、D²-RAG、S2G-RAG、QuCo-RAG、CUE-R、ReaLM-Retrieve。特别注意：S2G-RAG 已做充分性+gap query；D²-RAG 已做是否检索+噪声上下文处理；CUE-R 已做干预式证据效用；ReaLM-Retrieve 已联合 timing/query 和答案—成本奖励。

## 7. 必须允许的反证

强基线：`Always-Retrieve + Post-Retrieval Filter`。

若其最终答案、污染率和实测延迟与 CURA 相当，则应承认当前本地检索设置下“何时发起检索”没有足够价值，主问题应转向“何时使用证据”。不能为了保留 timely retrieval 而回避该结果。

## 8. 第一阶段科学诊断

在多个生成检查点，对每个问题构造：

- skip；
- 当前查询真实 top-3；
- gold supporting facts（若数据集提供）；
- 随机/无关文档；
- 冲突/反事实文档（后续扩展）。

用于区分查询失败、语料失败、证据利用失败、污染、不需要检索和时机错误。

核心指标：最终 EM/F1、真实 `B_t(q)`、beneficial retrieval precision/recall、负收益检索率、正确→错误/错误→正确翻转、supporting-fact Recall@k、收益校准与 risk-coverage。检索次数、延迟和上下文 token 只作次要指标。

## 10. 待审核实现方案 v1（2026-07-17）

### 10.1 总体顺序

1. 冻结 legacy ETC 和两个答案抽取器；新建 `baselines/ETC/research/`，不改旧算法文件。
2. 新 runner 生成无检索/ETC 轨迹并抽取最多 3 个检查点：首次 ETC 触发、首个句末、答案标记前；去重后保留按时间排序的状态。
3. 每个状态构造候选：原始问题、开源 ETC-QFS（仅在可用状态）、固定 prompt 生成的单个 prefix-gap query。
4. 从完全相同的 prompt+prefix 执行 skip 与各查询的检索分支；MVP 当前动作后不再允许第二次检索，用于隔离单次干预效应。
5. 用统一 `first_answer_span_v1` 计算终局 F1/Accuracy 和 `B_t(q)`；同时保存原始抽取作敏感性分析。
6. 先报告收益分布、查询 oracle、时机 oracle、负收益与翻转率；只有存在足够 oracle 空间才训练控制器。
7. 控制器主模型为冻结 Llama 状态表示/查询表示 + 小型 PyTorch MLP，Huber 回归与同状态动作排序联合训练；tabular-only 模型作消融。
8. 校准按 qid 分组，在每个校准问题上取所有时刻和查询的最大高估残差，得到保守的一侧校准项；推理时执行最早 `max_q LCB_t(q)>0` 的查询。
9. 同时实现 `CURA-pre`（检索前预测）和强反证 `CURA-post/Always-Retrieve+Filter`（先进行廉价检索、看到文档后决定是否注入）。

### 10.2 MVP 约束

- 数据集：先 HotpotQA/2Wiki；训练/校准按 qid 隔离，目标数据集不调阈值。
- 每题最多 3 状态、每状态最多 3 查询、最多实际注入 1 次。
- 检索与证据注入保持 ETC 当前 top-3 和单句再生成语义；所有新方法使用同一 canonical runner。
- 结果分层保存为 `states.jsonl`、`actions.jsonl`、`retrievals.jsonl`、`manifest.json`，支持分片、逐条 flush、断点续跑和完整性检查。
- 首轮先做 20 条 smoke；随后 50～100 题诊断；oracle 不成立则停止，不直接扩到完整训练。

### 10.3 预设 go/no-go

- 候选 `oracle(t,q)` 相对最佳固定查询/固定时机至少有约 1.5～2.0 F1 点潜在提升；
- 有害动作或正确→错误翻转不是接近零的极小事件；
- 最佳检索位置不是几乎全部集中在同一个固定时机；
- 若 `Always-Retrieve+Filter` 与 CURA-pre 相当且实测开销很低，则主线转为“及时证据使用”，不强行保留 pre-retrieval gate。

以上阈值是用户已审核的预注册建议，不是已观测结果。

# 13. 2026-07-18：20 条反事实采集结果与协议审计

## 13.1 已确认事实

- 运行目录：`baselines/ETC/result/cura_hotpotqa_mvp_smoke20_de845ce_3gpu`。
- 完整性：20 个样本、58 个状态、192 个动作、134 个 retrieve 动作；审计 `complete=true`，错误列表为空。
- 运行耗时：53 分 59 秒，约 161.97 秒/样本。每个样本实际执行多条反事实生成分支，因此不能把该数值当成 CURA 部署推理延迟。
- 按 `first_answer_span_v1` 和 F1 计算，retrieve 相对同状态 skip 的动作计数为正 14、零 111、负 9，平均动作收益约 `+0.0198`。
- 按检查点的原始平均配对收益：首次 ETC 触发约 `+0.1116`，首句约 `+0.0521`，答案前约 `-0.1364`。这些只是 20 条诊断统计，尚未做独立样本置信区间或显著性检验。
- 查询候选的原始平均收益：ETC-QFS 约 `+0.0833`（n=18），prefix-gap 约 `+0.0349`（n=58），原问题约 `-0.0150`（n=58）。不同查询的可用状态数不同，不能直接据均值排名。

## 13.2 已确认的协议缺陷

- 汇总器检测到 `skip_vs_no_retrieval_max_abs_diff=1.0`，共 11 个 skip 不一致状态。即从某个检查点续写的 skip 并不总是复现原无检索轨迹的后续答案。
- 因此当前约 `+0.393` 的样本级 timing-query oracle 增益无效，不能作为主假设成立或 go/no-go 的证据。跨检查点 oracle 必须建立在同一 canonical trajectory 的精确 token 级反事实续写上。
- 初步人工检查 9 个负 F1 动作：6 个主要是正确的 yes/no 后增加解释而被抽取器判错，1 个是语义正确的缩写扩展导致词面 F1 下降，只有 2 个较明确表现为错误证据或错误使用造成的实质伤害。因此“答案前检索有害”和“负收益即噪声污染”目前都没有被证实。
- prefix-gap 查询中出现 `Show more`、`read more`、说明文字、截断和 OR 片段等生成污染。此现象已保留原文用于审计，不能在没有版本化规则与消融的情况下静默清洗。

## 13.3 初步解释与待验证假设

- 合理推断：在部分样本中，检索动作确实产生了知识性改善；人工检查发现 Animorphs、YG Entertainment、1999 等多例从错误答案转为正确答案。这说明查询特异的状态收益不是纯粹的数值噪声。
- 待验证：首次 ETC 触发是否真的是较稳定的查询就绪窗口。当前均值支持该方向，但样本太少、动作相关且评测协议有污染。
- 待验证：检索噪声是否是主要负效应来源。当前多数负 F1 来自生成格式/抽取污染，尚不足以支持该叙事；后续必须把语义伤害、检索失败、证据利用失败和评测污染分开标注。

## 13.4 下一版协议门禁

1. 状态必须保存精确 `prefix_token_ids`，分支续写不得用 prefix 文本重新分词来近似同一状态。
2. 同一状态的 skip 必须与 canonical continuation 在 token 或冻结答案协议上完全一致；任何不一致都使跨时机 oracle 审计失败。
3. 新增版本化答案终止/抽取协议，用于识别答案后解释污染；`first_answer_span_v1` 继续并列报告，不能覆盖。
4. 修复后先复跑相同 20 条并要求一致性门禁通过，再进行 50～100 条科学诊断。
5. 加速方向是复用一次无检索完整轨迹、批处理同状态分支并减少不必要的重复 forward；它改变采集效率，不应改变反事实动作定义。

## 14.3 解释边界

- 已确认：精确 token 协议下，存在真实的查询特异正收益；典型知识修正包括 Animorphs、YG Entertainment、1999、New York City 等。
- 已确认：v1 同时放大正收益和负收益，答案后解释会双向污染词面 F1；因此论文不能只报 v1。v2 更保守，且 Accuracy 下没有 correct-to-wrong 动作。
- 合理推断：首次 ETC 触发附近可能是更好的“查询就绪窗口”，而答案标记前才检索通常过晚。
- 待验证：上述时机差异能否跨更多样本和数据集保持；20 条样本不能支持显著性、新方法优越性或泛化声明。
- 待验证：ETC-QFS 是否真正优于其他查询。它只在 18 个动作中可用，不能与各 58 个动作的 question/prefix-gap 均值直接比较。
- 下一阶段可进入 50～100 条诊断，但统计单位必须是 qid，使用样本级 bootstrap，并继续并列报告 v1、v2 和 Accuracy。
